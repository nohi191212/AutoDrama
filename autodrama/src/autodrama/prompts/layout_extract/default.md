# 任务

根据全剧完整正文，维护后续长剧集镜头生成会用到的结构化场景视觉资产表 `layouts`。

这个节点只做场景资产提取、补充和延续判断，不写生图 prompt，不写画幅、镜头参数、模型名称或图片生成建议。

# 输入

全剧完整正文 novel_full_all_episodes：
{{novel_full_all_episodes}}

已有场景资产 existing_layouts：
{{existing_layouts}}

# 输出字段

只输出符合 JSON schema 的对象：

- `layouts`：数组，每项是一个场景视觉资产。
- `notes`：可选，简短说明本轮新增、保留或调整的依据。

每个 layout 必须包含：

- `name`：资产名。基准场景用短名称，例如「医院走廊」；状态变体建议用「场景名_状态」，例如「医院走廊_停电后」。
- `group`：空间组名。同一物理空间的 base 和 variant 必须共享 group，通常等于基准场景名。
- `asset_role`：只能是 `base` 或 `variant`。
- `reference_asset_name`：base 必须为空或 null；variant 必须填写它参考的 base 场景 `name`。
- `episode_keys`：该场景或状态实际出镜、实际延续出现的 episode_key 数组。
- `source_chapters`：可选，来源章节名数组。
- `brief`：一句话说明这个场景资产的空间功能、稳定可见特征，以及为什么会成为镜头参考图。
- `space_features`：base 写稳定空间特征列表；variant 通常留空或只写仍需强调的固定锚点。
- `state_delta`：base 必须为空字符串；variant 必须只写相比 reference base 发生的视觉状态变化。

# 场景资产一致性的根

layout 一致性的根是“空间组 + 基准空间结构”。

- `base` 是基准场景资产，用来锁定空间类型、入口、墙地顶或天空边界、固定结构、固定陈设、材质关系、可行动线和镜头锚点。
- `variant` 是同一空间的状态变体，必须基于某个 base，只改变状态，不改变空间拓扑。
- 状态变体适合表达昼夜、天气、灯光、停电、火灾后、战斗后、仪式后、污染、烟尘、水渍、破损、陈设被明显扰乱等会影响参考图的视觉变化。
- 如果空间拓扑、室内外边界、楼层、入口关系、核心功能区发生本质变化，应另建 `base`，不要当作 variant。

# 提取 / 不提取

提取：

- 故事真实发生、角色实际行动、对话、对峙、追逐、探索、仪式、战斗或关键情节推进所在的空间。
- 回忆、照片、视频、梦境中被镜头实际可视化呈现的空间。
- 会被后续多次复用，或即使只出现一次但对镜头调度非常关键的空间。
- 空间中的固定结构、建筑构件和稳定环境锚点应写入对应 layout 的 `space_features`，例如石台、祭台、台阶、门窗、柱梁、屋檐、道路、假山、池塘、花木、栏杆等；不要因此单独新建 prop。

不提取：

- 只被台词提到、背景设定里出现、角色没有实际进入或画面没有实际呈现的地点。
- 纯天气、纯情绪氛围、纯光效、纯镜头角度、纯道具/车辆/服装特写。
- 人物、道具、组织名、城市名等没有明确可画空间边界的概念。

# 合并与拆分

- 同一空间的正式名、俗称、功能称呼、局部称呼、镜头角度称呼要合并到一个 group。
- 不要因为一次性动作、临时人物站位、临时道具摆放、镜头角度、远近景变化而拆分场景。
- “学校”“医院”“公司”这类大地点如果正文实际镜头落在不同独立区域，应拆成「学校教室」「学校操场」「医院病房」「医院走廊」等 base。
- 同一房间的门口、中央、角落、窗边通常不拆；把这些写入 base 的空间特征。
- 没有明确状态变化时，后续场次延续上一个已确认的 base 或 variant，不因换场次就新建资产。

# 输出要求

- 输出必须是完整 `layouts` 数组，不是只输出新增项；已有合理资产要保留。
- 所有 `episode_keys` 只能使用输入正文中真实出现的 episode_key，不要自造 key，不要输出空数组。
- `brief` 和 `state_delta` 不要写完整生图 prompt，不要写画幅、镜头参数、模型名称、路径、URL、文件名、节点名或项目 ID。
- base 的 `state_delta` 必须为空字符串。
- variant 的 `reference_asset_name` 必须指向本次输出中存在的 base 场景名。
- 输出必须符合调用方提供的 JSON schema。
